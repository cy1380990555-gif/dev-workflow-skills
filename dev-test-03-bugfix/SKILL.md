# 测试-03: Bug修复

分析系统测试中发现的缺陷根因，修复代码并防止回归。

## 触发条件

- 系统测试发现缺陷，需要修复
- 用户提到 "Bug修复"、"缺陷修复"、"修Bug"、"bug fix"
- 测试不通过，需要修复后重新测试

## 执行步骤

### Step 1: 缺陷确认和分类

```markdown
## 缺陷确认

### 待修复缺陷清单
| 编号 | 标题 | 严重程度 | 模块 | 状态 |
|------|------|---------|------|------|
| BUG-001 | | 🔴致命 | | 待确认 |
| BUG-002 | | 🟡严重 | | 待确认 |

### 修复优先级
1. 🔴致命缺陷 — 必须立即修复
2. 🟡严重缺陷 — 必须在发布前修复
3. 🔵一般缺陷 — 建议修复，可带病上线
4. ⚪轻微缺陷 — 可延后修复
```

### Step 2: 根因分析

```markdown
## 根因分析: BUG-XXX

### 5 Whys 分析
1. **为什么出现这个问题？** → [直接原因]
2. **为什么会出现这个直接原因？** → [深层原因]
3. **为什么会出现这个深层原因？** → [更深层原因]
4. **为什么会导致这个更深层原因？** → [根本原因]
5. **为什么会产生这个根本原因？** → [流程/规范缺陷]

### 根因分类
| 类别 | 说明 |
|------|------|
| 🔴 代码逻辑错误 | 条件判断/计算错误 |
| 🟡 需求理解偏差 | 实现与需求不一致 |
| 🔵 边界条件遗漏 | 未处理的特殊场景 |
| ⚪ 环境配置问题 | 配置/环境差异导致 |
```

### Step 3: 修复方案设计

```markdown
## 修复方案: BUG-XXX

### 修复方案
**方案**: [简要描述修复方式]

**修改文件**:
| 文件 | 修改内容 |
|------|---------|
| | |
```

### Step 4: 修复实现

每个修复添加对应的回归测试用例。

### Step 5: 回归验证

验证修复有效且无副作用。

### Step 6: 修复统计

```markdown
## 修复统计

### 按严重程度
| 严重程度 | 总数 | 已修复 | 未修复 | 修复率 |
|---------|------|--------|--------|--------|
| 🔴致命 | | | | |
| 🟡严重 | | | | |
```

## 修复原则

1. 修复根因而非症状
2. 每个修复添加测试
3. 最小修改原则
4. 不引入新缺陷
5. 及时提交

## 输出物

- 缺陷确认清单
- 根因分析报告
- 修复方案和实现记录
- 新增回归测试用例
- 回归验证结果
- 修复统计报告

## 质量检查清单

- [ ] 所有 🔴 致命和 🟡 严重缺陷已修复
- [ ] 每个修复有根因分析
- [ ] 每个修复有对应的回归测试
- [ ] 影响范围回归测试通过
- [ ] 未引入新的缺陷

## 交接条件

→ 返回 **代码编写** (dev-code-02-coding) → **代码审查** (dev-code-03-review) → **系统测试** (dev-test-02-testing) 循环

**循环上限**: 最多 3 次，超出升级给用户决策
